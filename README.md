## 实现说明

### 组件

- `Seqlock`：序列锁核心。`write(Runnable)` 执行写操作；`read(Supplier)` 乐观读，
  自旋重试到上限后**降级为加锁读**保证进展；`tryRead(Supplier)` 到上限直接抛
  `RetryLimitExceededException`，由调用方降级；`stats()` 返回统计快照。
- `ConsistentPair`：复合结构示例，两字段 `a`、`b` 满足不变量 `a+b` 恒定，
  演示一次读取多字段的整体一致性。
- `SeqlockStats`：读取次数 `reads`、累计重试次数 `retries`、重试率
  `retryRate = retries/reads`、单次最大重试 `maxRetries`，外加降级次数 `fallbacks`。

### 版本号协议（要求 1）

- 版本号偶数=数据稳定，奇数=写者正在修改。
- 写者进入：版本 +1（偶→奇）；写完（含异常）：再 +1（奇→偶）。
- 读者：读前取一次版本（必须为偶数）→ 读取全部字段 → 读后再取一次版本，
  两次相等才接受快照，否则重试。
- 内存语义：写者最终发布用 release 写，读者两次校验用 acquire 读，
  被保护字段因此可以是普通字段（无需 volatile/原子类）。

### 写者优先，为什么读者与写者之间不需要互斥（要求 2）

读者不持有任何锁，只做"读版本→读数据→校验版本"的乐观尝试，失败即重试，
所以读者永远无法阻塞写者，写者天然优先。唯一的互斥是**写者与写者之间**的
`ReentrantLock`：版本协议只解决"单写者 vs 多读者"，多个写者并发修改同一数据
仍需串行化。读者与写者并发时，读者靠版本校验发现并丢弃脏读（而非靠锁阻止写者），
所以两者之间不需要互斥。

### 自旋重试、上限与超限处理（要求 3）

- 读者读到奇数版本或前后版本不一致时，`Thread.onSpinWait()` 后重试。
- 上限可配置（默认 `1024` 次重试，构造器可调；0 表示首次失败即放弃）。
- 超限处理：`read` 退化为悲观加锁读（获取写锁后读取，与写者互斥）；
  `tryRead` 抛 `RetryLimitExceededException`。

### 复合结构不撕裂（要求 4、5）

一次 `read` 回调内读取所有字段并组装快照，只有前后版本一致时快照才被接受，
因此快照中所有字段必然来自同一版本。压测（4 写者 × 25000 次写 + 4 读者，
  见 `SeqlockConcurrencyTest`）中数十万次读取的 `a+b` 始终恒定，无撕裂。

### 读者饥饿：说明与缓解（要求 6）

纯自旋方案下，写者耗时过长或写过于频繁时，读者可能反复失败而饥饿。
本实现的缓解：

1. 自旋有界，超限后 `read` 降级为加锁读，以阻塞换取确定进展，不再空转烧 CPU；
2. 对延迟敏感的调用方可用 `tryRead`，超限后自行降级（读旧快照/排队/失败返回）；
3. 工程建议：写临界区保持短小、合并批量写、避免在写回调里做阻塞操作；
   必要时可进一步引入"写者让路"（写者发现等待的读者时短暂让出 CPU）。

### 统计（要求 7）

`stats()` 返回 `SeqlockStats`：成功读取次数、累计重试次数、重试率、
单次最大重试次数、降级加锁次数（额外）。读计数用 `LongAdder` 降低热点竞争。

## 任务提示词

以下为本题完整的 User Prompt 原文，两次执行必须使用完全相同的文本。

我们的读多写少数据用读写锁代价太高，写入很短但读取需要完全一致的快照。请从零实现一个序列锁（Seqlock）组件。仓库目前只有一个空的 Maven 工程（pom.xml 只声明 JUnit 5 与 AssertJ）。要求：1) 用版本号实现：写者进入时版本加一（变奇），写完再加一（变偶），读者读前后校验版本一致；2) 支持写者优先：写者不会被读者阻塞，需说明为什么不需要互斥；3) 读者自旋重试：读到不一致时重试，需给出重试上限与超限的处理；4) 支持读取复合结构：一次读取多个字段时必须整体一致，不得出现字段来自不同版本的撕裂；5) 正确性：并发压测下读到的数据必须始终满足字段间的约束关系（例如 a+b 恒定），需有测试证明；6) 支持写者长时间写入时的读者饥饿问题说明与缓解策略；7) 提供统计：读取次数、重试次数、重试率与最大重试次数；8) 测试覆盖版本校验、字段一致性、重试上限、并发不撕裂与统计；`mvn -q verify` 一条命令跑通。
